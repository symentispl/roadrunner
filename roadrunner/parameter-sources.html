Parameter Sources

A parameter source feeds a different set of values into each request — for example a different SQL query, a different Cypher query, or a different URL per user — instead of sending the exact same request every time.

Usage

roadrunner run <options> <sampler> <sampler_options>

<type> selects which parameter source implementation to use. Roadrunner ships one built-in type: csv.

CSV

The csv parameter source reads one row of parameters per request from a CSV file.

Key Required Description

file

Yes

Path to the CSV file

separator

No

Single-character column separator (default: ,)

 
roadrunner run -c 10 -n 100 --parameters-source csv:file=queries.csv jdbc \
  --url <jdbc_url> \
  --username <username> --password <password> \
  --driver <driver> \
  'query("SELECT * FROM users WHERE id = ?")'

The first row is the header and names the parameters; every row after it is one set of values. All rows are loaded into memory once before the test starts, then cycled through round-robin as requests are made — if there are more requests than rows, the file repeats from the first row. Given:

id
1
2
3

each request binds the next row’s id value to the query’s ? placeholder.

How columns are bound

Which column a sampler reads by depends on the sampler:

  • Samplers that bind parameters positionally (e.g. JDBC's ? placeholders) use column order — the first CSV column feeds the first placeholder, regardless of its header name.

  • Samplers that bind parameters by name (e.g. Neo4j's $name Cypher parameters) use the header name directly — a column must be named id for a query to reference it as $id.

  • The HTTP sampler uses column names in several ways: ${name} in the URL is replaced with column name’s value, a `header:<name> column becomes an HTTP header, and a body argument written as @<name> in the expression resolves that column’s value as the request body.

Either way, every value read from the CSV file is a plain string unless the column declares a type (see below).

Typed columns

By default every CSV value is passed to the sampler as a string, even if it looks numeric. Suffix a header with :<type> to convert it before it reaches the sampler:

name,age:int
alice,30
bob,25

Supported types:

Type Converts to

int

java.lang.Integer

long

java.lang.Long

short

java.lang.Short

float

java.lang.Float

double

java.lang.Double

boolean

java.lang.Boolean

file

java.io.File

A column with no :<type> suffix is left as java.lang.String.

This matters most for JDBC: an untyped column always binds as VARCHAR, so age:int is how a query like 'query("SELECT * FROM users WHERE age > ?")' gets a real INTEGER bound instead of a string the driver has to coerce.

Whether a converted value can actually be used still depends on the sampler binding it. The JDBC sampler supports int, long, short, float, double, and boolean, but has no mapping for java.io.File yet — a :file column bound into a JDBC ? placeholder fails at request time with unsupported Java type for JDBC parameter binding: java.io.File. The HTTP sampler, on the other hand, uses :file specifically to stream a request body from disk instead of loading it into memory as a string — see its body section.

Blank values

A blank cell is passed through as an empty string rather than converted — age:int with an empty cell yields "", not 0 or an error.

Errors

Roadrunner validates the header when the file is first loaded (before any requests are sent), so a bad header fails the test immediately rather than mid-run:

  • An unknown type (e.g. age:number) raises an error listing the supported types.

  • A header with more than one : (e.g. age:int:extra) raises an error.

  • Duplicate column names (after stripping the :<type> suffix) raise an error.
